## 界面结构（tab 顺序，v1.5 起）

导航顺序**只有这一处事实源**，其他小节只引用不重复：

```
🏠 项目 → 🗺 功能地图 → ⚡ 现在 → ⚖ 决策与待办 → 📖 术语表 → ❓ 使用指南
```

- 共 6 个 tab（v1.5 起；v1.3 是 5 个）。新增的「⚖ 决策与待办」插在「现在」与「术语表」之间，其余四个位置不变。
- 「现在」只放**进展时间线**，单列整宽（不再用两栏 `.cols`）。
- 「决策与待办」按四段排：**待拍板决策**（n 件）→ **已定决策**（折叠，summary 写「已定 n 件」）→ **待办**（未完成在上）→ **已完成**（折叠，summary 写「已完成 n 件」）。
  - 这四段任意一段为空时，空态文案一律是 **`暂无`**（评审稿 7.5 裁定）。**作用域仅限「决策与待办」这四段**：`#now` 的时间线空态（「还没有进展记录」）与其它既有空态**不动**。
- 「❓ 使用指南」tab 含两张新指南卡，标题与正文以 `references/copy-deck.md` **§7** 为定稿（本契约不复制文案，只钉住"这两张卡属界面固定文案、按 §7 实施"）。
- nav 按钮的 `data-tab` 与 section 的 `id` 一一对应，六个值固定为：`project` / `features` / `now` / `decisions` / `glossary` / `guide`。
- **「功能 | 技术」视图切换（v1.6 起）放「功能地图」tab 的工具栏**（`.ghead` 内、缩放控件左侧），**不新增 tab**：六 tab 的顺序与数量到此为止不再变。切到「技术」时只重建 `#features` 里的 `<svg id="graph">`；**图标题随视图切换**（**功能视图**用本来的图标题、不变；**技术视图**用与**空态标题同一个名称**的那个标题——空态标题形如「还没有」+ 该名称，**两者共用同一个名称，不是把空态整句拿去当图标题**；**两个标题的字面措辞以 `references/copy-deck.md` §3 的两行登记为定稿**，本节**只钉"标题必须跟着换"这条语义、不复制文案**），**图例与工具行保留**；视图状态存内存、不持久化（见「TECH.md」一节）。
  - **为什么标题要跟着换**（依据）：① 这一路的方向就是**人话**——用户切到技术视图必须**一眼知道自己在看哪张图**；② **自洽**——空态标题里点名的那个名称，**必须与视图标题是同一个名称**，否则用户看到的是两套叫法；③ 原来那句"标题保留"写在**"技术视图只是换个画法、仍是同一张图"**的假设下，**现在它是一个独立视图，假设已不成立**。
  - **单一事实源**：这条口径**只在本行走完整成句**；`graph-visuals.md` §F1（视觉侧头图结构）与本节「TECH.md · 界面」只**引用**它，不重复成句。
- 掌控条「等你拍板 ⚠ n 件」徽章点击**照旧打开拍板浮层**（不跳 tab）：评审稿 3.4 的裁定是"等你拍板那个不用改"，7.7 的"改跳 tab"作废；改法是在拍板浮层底部加一行跳转 `完整列表见「决策与待办」页 →`。本 tab 负责完整列表与待办，浮层负责快速拍板。

## PRODUCT.md

```markdown
# 项目名（一句话定位可跟在破折号后）

## 项目简介
一段人话：这是什么、给谁用、解决什么。禁止技术黑话。

## 当前方向
- 阶段: 报表开发中
- 方向: 把月度报表做扎实
- 下一步: 预算提醒

## 使用流程
1. 步骤标题 :: 一句话描述 :: 证据: src/index.html, docs/x.md
2. 第二步 :: 描述（证据可省略）
```

- 使用流程用有序列表，`::` 三段分隔；第三段 `证据: ` 前缀可选，多个证据用英文逗号分隔。

## FEATURES.md

```markdown
# 功能地图

## 功能: 记录收支
- 状态: 已验证
- 简介: 首页输入金额选分类，回车即存，3 秒记一笔。
- 证据: src/pages/record.js, tests/record.test.js
- 依赖: 无
- 验证: 用户在 2026-10-03 验证过

## 功能: 月度报表
- 状态: 进行中
- 简介: 按月汇总收支，出分类饼图。
- 依赖: 记录收支

### 子项: 分类汇总
- 状态: 已验证
- 简介: 按分类加总金额。
- 证据: src/pages/report.js
- 验证: 用户在 2026-10-06 验证过

### 子项: 饼图
- 状态: 进行中
- 简介: 把汇总画成饼图。

## 功能: 预算提醒
- 状态: 设想
- 简介: 设定月度预算，快超支时提醒你。
```

- `状态` 必填，取值仅限五态：`设想` / `进行中` / `可用` / `已验证` / `已废弃`。已废弃的功能**仍保留在文件里**（页面另做删除线样式），不是从文件删除。
- `简介` 必填，一句人话，≤40 字。
- `证据` 可选，工作区相对路径，英文逗号分隔；每个路径都受「证据路径红线」约束。
- `依赖` 可选，填其他功能的**名称**（同名匹配），逗号分隔；`无` 或省略表示无依赖。名字对不上时该条依赖被忽略（不报错）；功能重名按首个同名解析并给 WARN。
- `验证` 仅在状态为 `已验证` 时必填，记录谁在何时验证。
- **「已验证」必须有验证记录**：写了 `- 状态: 已验证` 却没有 `- 验证:` 行 → blocker（退出码 2），掌控条「数据健康」不健康。

### 子项（v1.3 起，可选）

- 功能块下可嵌套任意个 `### 子项: 名称`，表达"这个功能由哪几块组成"——面向**用户可感知的组成块**，不是开发步骤流水（开发步骤进 NOW.md 时间线）。
- 子项允许字段：`状态`（必填，同五态）、`简介`（必填）、`证据`、`验证`；**不允许 `依赖`**（依赖关系只在功能层表达；子项写了 `依赖` 会被忽略并给 WARN）。
- 子项的「已验证」同样必须有 `验证` 行，否则 blocker（与功能同纪律）。
- 子项名在同一功能内唯一；跨功能重名不冲突。同功能内重名给 WARN，按首个解析。
- 子项不进功能关系图的主布局、不计入顶部进度统计（进度条只数功能）；页面上默认折叠为父节点/功能卡上的「子项 n/m」徽标，点击展开。
- 子项的 `证据` 与功能证据同走「证据路径红线」与覆盖性审计（算归属该功能名下）。
- 功能的状态由人/agent 按整体判断填写，**不由子项状态自动推导**；子项只是拆解视图。
- 状态机纪律（含回退路径）：
  - 只能由人类盖章向前：设想 → 进行中 → 可用 → 已验证；agent 最多标到 `可用`。
  - 撤销验证：`已验证` → `可用`（功能没坏，只是撤回盖章；同时删掉该功能的 `- 验证:` 行）。
  - 返工重做 / 验证不通过：`可用` 或 `已验证` → `进行中`。
  - 废弃：任意状态 → `已废弃`；恢复：`已废弃` → `设想`。
  - 每次状态变更（含回退）都要在 NOW.md 时间线记一笔人话。

## 术语表（GLOSSARY.md，v1.3 起，默认建）

长项目里模型用词会漂（同一个东西前后叫法不一）。术语表是**用词的唯一对照标准**：写任何仪表盘文案前先对照它选词。它有自己的 tab（顺序见「界面结构」），不在「项目」页重复展示。

```markdown
# 术语表

| 标准用词 | 指什么 | 别名/曾用名 |
| --- | --- | --- |
| 开发仪表盘 | 本 skill 生成的产品看板 | 看板、dashboard |
| 拍板 | 用户在决策卡上选定选项 | 决定、定夺 |
```

- **文件名不写死**：认的是**表头契约**，不是文件名——叫 `术语表.md`、`词汇表.md`、`glossary.md` 都行，改名不用改任何配置。
- **识别优先级**（渲染器每轮按此顺序解析）：
  1. `dev-dashboard/.cyd.json` 里用户手写的 `{"glossary": "<文件名>"}`——最高优先，渲染器只读这一项、不覆盖；
  2. **内容嗅探**：`dev-dashboard/*.md`（排除 PRODUCT.md / FEATURES.md / NOW.md）里**唯一一个**第一张表表头符合契约的文件；
     - 候选枚举按**小写扩展名**认 `.md`（Windows 大小写不敏感、macOS / Linux 区分，显式按小写比较才能三端认同一批文件）；
     - **三大事实源文件名大小写敏感**：排除时用 `p.name in ("PRODUCT.md", "FEATURES.md", "NOW.md")`，**区分大小写**。事实源若写成 `product.md` / `Now.md`，它**不会**被当事实源排除，两端都会把它当**候选术语表**（行为两端一致但反直觉，别当 bug 改）。所以三大文件名必须逐字写成 `PRODUCT.md` / `FEATURES.md` / `NOW.md`；
  3. 命中多个 → **不猜**：不阻断渲染，产出一条 WARN（判据 = `glossary_source == "ambiguous"` 且候选数 ≥ 1）并在 `.cyd.json` 里记 `glossary_source: "ambiguous"` + 候选列表，由 AI 在对话里问用户一次并写回第 ① 项；**该 WARN 的逐字文案归 `references/copy-deck.md` §16.6（契约不内联中文）**（见「health 字段清单」的文案归属总则）；
  4. 一个都没有 → 不算错误，`glossary_source: "none"`，界面显示空态。
- **`glossStatus` 的两个失败 flag（v1.6 补录、不升版）**：识别结论对象除 `{file, source, candidates}` 外，**允许带两个可选 flag**，用来把"读 `.cyd.json` 时出的岔子"从**宿主**传给共享核——**修的是"面板比导出页少几条提示"这条跨端漂移**（清单 #11/#12）：
  - **`meta_error: true`**：`.cyd.json` **存在、读得到，但内容不是合法 JSON 对象**（解析失败或顶层不是 object）。
  - **`meta_missing: "<文件名>"`**：`.cyd.json` **合法**、其中 `glossary` 是非空字符串，但**该文件在工作区里不存在**（渲染器退回自动识别）。值就是那个不存在的文件名，便于把名字带进提示。
  - 二者**互斥**（JSON 都读不出来时无从得知 `glossary` 指向谁，只会有 `meta_error`）；都缺省时表示"`.cyd.json` 这一环没出岔子或压根没有该文件"。
  - **谁填**：**宿主**。三处都要填，且**不许再静默吞异常**——吞异常本身可以，但**失败事实必须作为 flag 传出去**：`plugins/dsh-plugin-control-your-development/src/client.src.js:133`、`templates/dashboard.web.js:74`、`plugins/control-your-development/smoke/js_assemble_driver.js:30`。Python 侧没有这一环（`resolve_glossary` 自己解析、自己判）。
  - **共享核据此产一条 WARN**：`assembleData` 见到 `meta_error` / `meta_missing` 各产一条与 Python **逐字同文案**的 WARN。**逐字文案归 `references/copy-deck.md` §16.6（契约不内联中文）**（见「health 字段清单」文案归属总则）。
  - **向前兼容（重要）**：flag **缺失 / `undefined`**（旧版宿主、或宿主环境拿不到 `.cyd.json`）→ **不产 WARN、不报错**。这是**降级**，不是"正常"：那种环境下面板就是**看不到**这两条提示，与导出页不一致是**已知代价**；升级宿主即可消除。**不得**把"缺 flag"当成"已检查且无问题"。
- **`resolve_glossary` 只允许一处实现（补录、不升版）**：这条判定逻辑（读 `.cyd.json` → 显式指定 → 内容嗅探 → 歧义 / none，外加上面两个 flag）**在全仓只允许一份**。现状有 **3 份**（Python `render_dashboard.py:resolve_glossary`、JS driver `js_assemble_driver.js:27-41`、宿主各一份候选名 fallback），违反 `AGENTS.md`「单一执行路径」，也正是 #11/#12 差异的来源；收敛到哪一份由实现者定（Python 或共享核），其余必须改成它的**薄封装**（只做 IO 注入，不重复判定）。
  - 若选"**共享核暴露契约化入口**"，其形状照此实现（**输入全靠注入、函数本身不碰 IO**）：
    - 输入：`{ metaRaw: string | null, listMd: string[], readText: (name) => string | null }`（`metaRaw` = `.cyd.json` 原文或 `null`；`listMd` = `dev-dashboard/*.md` 的文件名列表，**大小写比较口径同契约**；`readText` 用于读候选文件的第一张表头）
    - 输出：`{ file, source, candidates, meta_error?, meta_missing? }` —— 与 `.cyd.json` 的三项同名，外加两个 flag；`source` 取值集合不变。
    - **双向约束**：Python 与 JS 都必须能只靠这三个注入参数复现同一结论（差分门禁 `dual_parser_diff.py` 会拿它比对面）。
- **表头契约**：第一张表的表头 ≥3 列，首列是 `标准用词`（也接受 `术语` / `用词` / `Term` / `Glossary Term`，大小写不限），其余照旧为 `指什么` / `别名/曾用名`（顺序固定，分隔行 `| --- |` 有无均可）。别名多个用 `、` / `，` / `,` / `/` 分隔（四种，两端正则 `[、，,/]` 一致）；别名列可空。
  - **别名本身含 `/` 时（如 `CI/CD`）会被切成两个别名**——请改用 `、` 或 `，` 分隔，或避开该写法。`/` 是契约已定的分隔符，为不破坏已有表格，行为不改。
- **别名解析顺序：先 strip 再滤空**（两端同口径：`[a for a in (x.strip() for x in 分隔后) if a]`）。顺序不能反——"先滤空再 strip"会让**只剩空白**的项通过滤空、strip 后变成**空别名**，而空串能在正文任意位置匹配，直接造出**假漂移**（实测旧逻辑会假报 3 条）。两端另各兜一道 `if not alias or alias == 标准用词: 跳过`。
- **诞生时机**：init 时**默认一并建立**——从项目现状（代码标识符、文档、PRODUCT/FEATURES/NOW 里出现过的不同叫法）抽初稿；项目确实一片空白、没有任何固定叫法时，建骨架（表头 + 一行注释说明"待补充"），不编内容。存量项目 / 中途启用：每次 update / verify / 渲染都做一次体检，解析不到就**在对话里问用户**是否生成（一句话说清价值，得到同意再建），**不许静默创建**；用户也可以整份删掉。
- 解析失败的行（列数不够等）忽略并给 WARN；文件在但第一张表表头不符契约 → WARN 提示正确格式，按"无术语表"处理（不自动改写用户文件）；文件里压根没有表格也会给 WARN。
- **漂移检查**（非阻断，进 `warnings` 与 `health.glossary_drift`）：任何别名的字面出现在 **PRODUCT.md / FEATURES.md / NOW.md 正文**里（先剥离 `<!-- -->` 注释）即产出一条 WARN（每条 `alias / term / file / count` 一份，**同一（别名, 文件）只报一次**；标准用词本身的正常使用不报；检查范围**只限这三份正文**，不查术语表自己）。**该 WARN 的逐字文案归 `references/copy-deck.md` §16.6（契约只钉判据、不内联中文）**（见「health 字段清单」的文案归属总则）。
- **界面按状态分四种**：① 有表 → 表格 + 漂移明细；② 歧义 → 提示指定文件名；③ 无表 → 空态：讲价值 + 给格式 + 一键"让 AI 建立术语表"（面板里这句话直接进主对话，离线网页退回复制）；④ 文件在但表头不符 → 提示正确格式。
- **来源始终可见**：术语表 tab 底部永远标注"来源：<真实文件名>"；掌控条「数据健康」里也永远有一行术语表状态（正常 / 未启用 / 歧义）。
- **真实文件名只能从 `.cyd.json` 读**：面板没有列目录能力（只能按路径读文件），所以渲染器每轮都把解析结论写进 `dev-dashboard/.cyd.json`（字段见「机器文件与 `change` 取值」），界面据此才知道术语表叫什么。

## CHANGES.md（变更规则，v1.6 起）

> 默认随 init 一并建立。它是**项目自己声明**的"什么改动算产品变更 / 某类改动归到哪个功能或模块"的人话规则；有了它，采集来的变更不必每轮都靠 AI 现场猜归属。与 `TECH.md` 合称**声明类文件**（below 的归置与防后门规则对两者同样生效）。

- **文件名不写死，按内容识别**（与术语表同构的四级链）：
  1. `.cyd.json` 里用户手写的 `{"changes": "<文件名>"}`——最高优先，渲染器只读不覆盖；
  2. **内容嗅探**：`dev-dashboard/*.md`（排除三大事实源与已识别的术语表）里**唯一一个**满足判据的文件；
  3. 命中多个 → **不猜**：`changes_source: "ambiguous"` + 候选列表，AI 在对话里问用户一次并写回第 ① 项；
  4. 一个都没有 → 不算错误，`changes_source: "none"`，界面给空态 + 一键"让 AI 建立变更规则"。
- **识别判据（任一命中即认）**：① 第一个二级标题是 `## 内部工程` 或 `## 变更归属`；② 第一张表表头三列为 `路径/变更类型`（也接受 `路径` / `类型` / `文件`）| `归置方式` | `归属`。
- **最小骨架**（init 时从 `FEATURES.md` + 证据路径 + `依赖` **推出**，不是让用户从零写）：

  ```markdown
  # 变更规则

  ## 内部工程（不算产品变更）
  - tests/**、*.lock、.github/** → 归置方式: 忽略

  ## 变更归属
  | 路径 / 变更类型 | 归置方式 | 归属 |
  | --- | --- | --- |
  | src/pages/** | 记进时间线 | 功能「月度报表」 |
  ```

- **推导纪律**：把每个功能的证据路径按目录归并成条目、把功能的「依赖」写成归属提示；**推不出来的条目留 `[待确认: 这条改动怎么归置]`，不许编**。用户手写过的条目，AI 不许用推导结果覆盖。
- **漂移 WARN**（非阻断，进 `warnings` 与 `health.changes_drift`）：出现下列任一情形即产出一条 WARN：规则引用的功能/模块名不在当前地图里、或规则的路径不再出现在任何功能的证据里。**判据在契约、逐字文案归 `references/copy-deck.md` §16.6（契约不内联中文）**（它同样进 `warnings[]`，两端必须逐字同文案；契约不内联中文，同「TECH.md · 审计与 WARN」的归属规则）。**为什么**：这份文件是**推导出来的**，功能地图变了它不会自己更新；不提示就是静默腐烂。
- **算不算"已归置"？算——但审计必须单列（防后门）**：
  - **算**：CHANGES.md / TECH.md 里声明的路径计入归置集合（否则用户在规则里写清楚了，审计还一直报"未归置"，规则文件等于白写）。
  - **单列**：审计弹层**固定**分两行显示（0 条也显示），两端落成 `health.declared_refs`。**标签与计数单位必须对齐**（单位不同、标签就不能都写"文件"，那是"静默错"）：
    - `仅由变更规则声明的路径：N 条` —— **单位 = 声明条目**（CHANGES.md 的一行可能是一条 glob，如 `src/pages/**`，不是文件）；
    - `仅由技术地图引用的文件：N 个` —— **单位 = 具体路径/文件**（TECH.md 的模块证据是具体路径）。
    - **为什么**：只算归置而不单列，任何人把全部变更往这两份文件里一写就能把「未归置」清零 —— 那是把覆盖性审计变成走过场；可见性是最低成本的防线。
  - **`changes_only` 的判定口径（glob，不做成员判断）**：CHANGES.md 声明的是**路径模式**，无法与具体证据路径直接做成员判断；**枚举文件系统又会破坏两端同构**（JS 没有目录枚举能力）。因此：**声明条目若能以 glob 匹配到任一"已被功能／使用流程／时间线引用"的路径 → 视为已被引用（不计入 only）；匹配不到任何一条 → 计入**。匹配语义与 `.dashboard-ignore` 同款（`*` 不跨目录、`**` 跨目录、`?` 单字符、大小写敏感）。
  - **CHANGES.md 的规则行不做文件系统存在性 check**（与 TECH 的**不对称**，必须写明）：
    - TECH.md 的 `证据` 走**完整红线**（越界 / 不存在 → 报警，越界算 blocker）；
    - CHANGES.md 的规则行**只参与"算归置 + 审计单列"，不查存在性**；
    - 但**仍查"地图漂移"**（引用的功能/路径已不在当前地图 → 上一条那个 WARN）。
    - **为什么**：glob **没有"存在性"可查**；要查就得枚举目录，**破坏两端同构（JS 不能）**；而地图漂移检查已经能抓"引用了不存在的东西"这一类。
  - **不参与 `ok`**（不新增 blocker）；但这类路径**超过 10 条**时给 WARN 提示复核。若日后要收紧为 blocker（会改退出码），须另开契约变更，不许顺手改。

## TECH.md（技术地图，v1.6 起）

> 默认随 init 一并建立（用户已拍板）。**定位一句话：功能地图答"用户能得到什么"，技术地图答"这些东西是怎么搭起来的"。** 两者共用同一批证据路径，靠交叉引用互相显示，**不另做第三张图**。

- **文件名与识别**：与 CHANGES.md 同一套四级链（`.cyd.json` 的 `tech` 字段 → 内容嗅探 → 歧义就问 → 没有给空态）；嗅探判据：第一个二级标题是 `## 模块`，或第一张表表头同时含 `模块` / `层` / `技术` 三列。
- **字段固定七项（含 `### 子项` 复用）**：

  ```markdown
  # 技术地图

  ## 模块: 报表渲染
  - 层: 界面
  - 职责: 把月度汇总画成饼图，悬停显示金额
  - 技术: Canvas 2D
  - 状态: 可用
  - 证据: src/pages/report.js
  - 连到: 汇总服务（HTTP 调用）, 本地缓存（读）

  ### 子项: 图例渲染
  - 层: 界面
  - 职责: 画分类色块与名称
  - 技术: Canvas 2D
  - 状态: 进行中
  - 证据: src/pages/report.js
  ```

  - `模块` 必填，名字即主键；同文件内重名给 WARN 并按首个解析。
  - `层` 必填，**自由文本，不预设词表**；**纵向位置由"首次出现顺序"决定** —— 解析结果里给 `tech.layers = [...]`（按首次出现去重排序），视觉侧照这个顺序自上而下排，**不许在渲染核里硬编码层名单**（`graph-visuals.md` §F2 现写的五个层名需按本条同步）。
  - `职责` 必填，一句人话（≤40 字，与功能简介同纪律）。
  - `技术` 可选，点名到具体（`SQLite`、`Canvas 2D`）。
  - `状态` 必填，**复用功能五态**（设想 / 进行中 / 可用 / 已验证 / 已废弃），语义 = 这块实现的落地程度；同样受 `static/core/stance.md` 的状态机纪律（AI 最多标「可用」）。
  - `证据` 可选，工作区相对路径、逗号分隔，受「证据路径红线」约束；**计入归置**，并与 CHANGES.md 一起在审计里**单列**（防后门，规则同上一节）。
  - `连到` 可选，格式 `目标模块名（关系文字）`，逗号分隔；目标不存在或已废弃 → **幽灵边**，判定与样式**复用 `references/graph-visuals.md` §B（B1 判定 / B2 样式 / B3 标记）**，不另立一套。
  - `### 子项:` 复用功能地图的子项机制：同五态、必写证据、**不写 `连到`**；子项不计入顶部统计。
- **审计与 WARN**（见下各条，**全部非阻断**）。**文案归属规则（先读）**：这些 WARN 都会进 `warnings[]`（`dual_parser_diff.py` **逐条比对**的字段）或审计弹层「其他提示」，因此**逐字文案一律归 `references/copy-deck.md` §16.6（契约不内联中文）**，**契约只钉两件事：① 触发条件（判据）② 两端必须逐字同文案**。**契约里不再写这些 WARN 的中文**——再写一遍就是第二份事实源，正是 `copy-deck.md` 刚抓到的那类错误（契约「`⏳` 明细浮层」一条曾把四个类型词内联进来，`AGENTS.md`「界面文案」一行：契约只钉语义、不复制文案）。
  - `证据` 走同一套「证据路径红线」：越界 / 不存在 → 报警；**越界算 blocker**（触发条件本身就是判据，无需文案）。
  - **模块重名** → WARN（非阻断）：同一文件内两个模块同名时**按首个解析**并产出一条 WARN。逐字文案归 `references/copy-deck.md` §16.6（契约不内联中文）。
  - **缺 `层:` / 缺 `职责:` → 各一条 WARN，不降级为静默容错**：两条都保留为**用户可见提示**。**为什么**：缺 `层` 会让模块落到**错误位置**（纵向位置=层的首次出现顺序），用户看着图不对却**看不出为什么**；缺 `职责` 则模块在图里只剩一个名字。所以宁可烦一点，也不许静默补默认值。
  - `连到` 指向不存在 / 已废弃的模块 → **不报错**，画**幽灵边**（判定与样式复用 `references/graph-visuals.md` §B）。**它不是 WARN，不涉及文案归属。**

    - `update` 时的两条漂移检查：
      - **原有模块的证据路径一条都不存在了** → 一条 WARN。**判据 = 与上一轮的 `TECH.md` 对比**（不是"本轮证据为空"——单看本轮无法区分"删了证据"与"本来就没写"）。

- **算法纪律**：① 依赖图要先做**环检测**（`warnings` 已有依赖环提示），闭包遍历带已访问集合截断，**环不许造成死循环或重复计数**；② `依赖` 指向不存在/已废弃功能的边**不进闭包**（它们由幽灵边表达，见 `graph-visuals.md` §B）；③ 该派生**纯前端**：不写进内嵌数据、不进 `dual_parser_diff.py` 的比对面，但**算法只能有一处实现**（共享核里一个函数），不许 Python 与 JS 各写一套。
- **为什么纯前端**：这是"用现有数据现场算出来的视图"，不是新的事实源；把它算进内嵌数据只会多一份要两端逐字对齐的字段，收益为零、漂移风险为正。

## 证据路径红线

`证据` 行（功能、使用流程、时间线三处都算；**v1.6 起技术地图的模块证据也算**）里的每个路径必须：

- 是相对**工作区根目录**（`dev-dashboard/` 的父目录）的路径，`/` 或 `\` 分隔都行，渲染器会统一归一化；
- 不是绝对路径（以 `/` 开头）、不是盘符路径（Windows 上以「盘符 + 冒号」开头的那种）、不是 UNC 网络路径（以两个反斜杠开头的那种）、不含上跳段 `..`（即不允许出工作区）。

违反红线一律按"证据不存在"处理：证据矩阵里 `exists=false`、掌控条「数据健康」报警、渲染退出码 2（blocker）。越界路径单独统计在 `evidence_invalid` 里。渲染器对同一条路径只检查、只记一次。

## 机器文件与 `change` 取值

- `.state.json`：**只记采集游标** `{"last_collect": "ISO8601", "files": [...]}`（批 4 已实现；旧文件里的 `pending_items` **兼容读后直接忽略**，写回即消失），采集器维护，人手勿改。**注意这句说的是"本版只*写*这两个键"（不自己发明新键）**，**不是"这份文件只能有这两个键"**——**他人/他版写的未知键按「保留未知键」条款原样保留**（见「升级与兼容」§三·1）。**累计未归置集合的唯一事实源是 `.facts.json` 自己**（见下「同步链路 5 项改进」第 1、2 条）。
- `.facts.json`：`{"generated_at": "ISO8601", "source": "git|mtime(...)", "items": [{"path": "...", "kind": "code|doc|test|other", "change": "added|modified|deleted"}]}`。`source` 是采集来源（有 git 用 git，无 git 退化为文件修改时间），渲染器原样透出到 `health.source`，网页据此标明来源。
  - `change` 取值只有三种：`added` / `modified` / `deleted`。**删除事件同样必须归置**：时间线记一笔（"某文件已删除 / 被替换"），或写进 `.dashboard-ignore`。
  - 文件不存在 = 还没采集（页面提示待采集，不算不健康）；文件存在但 JSON 解析失败 = 不可审计（`facts_error` 为 `corrupt`，blocker，退出码 2）。
- 采集来源（git / 文件修改时间）会标明在网页上：有 git 用 git（含已提交与未提交），无 git 退化为 mtime 扫描。
- `.inbox.jsonl`（v1.3 起；`type` 取值集合 v1.5 明确）：面板拍板/指令的兜底信箱，一行一个 JSON 对象，字段固定三个：`{"ts": "ISO8601", "type": "<见下>", "text": "<完整消息原文>"}`。
  - `type` 取值集合**只有这四个**，不再扩充（v1.5 的待办勾选复用 `command`）：
    - `decide`：面板拍板。`text` 是完整拍板消息（含决策编号与所选选项）。
    - `verify`：**保留值，当前没有发送方**。面板的「我已验证」有意走 `command`——它是一次"工作请求"（请 agent 写文件 + 记时间线），不是单纯的状态写回，不为对称再造第二条路径。批 2 不扩充 `type` 集合、不新增发送方。
    - `command`：改状态的指令，含待办勾选 `待办「X」我做完了，记一笔`。
    - `ask`：节点面板/快捷追问的一句提问（只问，不改状态）。
  - **"待生效"语义**：只要这一行还在 `.inbox.jsonl` 里没被 skill 收取，它就是"待生效"；被收取（逐条落进三份 Markdown）并清空文件后才算生效。界面上的 `⏳ 待生效 N 条` 与待办行的「已报 · 待生效」都指这个状态，**不是**"已写进产物"。
  - skill 的 update 模式**开头先收取**：逐条翻译成三份 Markdown 的改动（`decide` → 改决策状态；`verify` → 改功能状态 + 时间线；`command` / `ask` → 按内容执行），处理完清空该文件（写空或删除）。人手勿改。
  - 取值三态（与「health 字段清单」的 `inbox_pending`、同步点 #6 同一口径）：文件不存在或为空 → `health.inbox_pending = 0`；**读取失败（IO／权限）→ `null`**（掌控条显示 `⏳ 待生效 —`）；读到就按未收取行数给整数。**这三种都"不算不健康"，都不进 `ok` 判定**（`0` 不是失败，`null` 也表示"读不到"而非"有问题"）。
  - **逐条内容同源**：`health.inbox_items`（每条 `{type, text}`）必须从**同一次读取**的文本解析出来，不许为它再读一次文件——两次读取会造出"计数与明细不一致"的第二事实源（详见「health 字段清单」）。
  - **读取失败不写 `warnings[]`（实现约束）**：`warnings` 是两端**逐条比对**的字段，而 JS 侧只拿得到 `inboxRaw = null`（看不见 OS 错误原文），写进去必然分叉；失败状态由 `inbox_pending = null` 本身表达。将来若要加 IO 失败提示，**只走 stdout**，不进 `warnings`。
  - 整行无法解析成 JSON 对象 → 跳过该行并给 WARN，不阻断。
- `.cyd.json`（v1.3 起；**v1.6 扩到三份声明类/对照文件**）：**渲染器拥有**的机器文件，记录"文件名不写死"那几份文件的解析结论——面板没有列目录能力，靠它才知道真实文件名。字段：
  `{"version": 1, "glossary": "<用户手写>", "glossary_file": "术语表.md" | null, "glossary_source": "explicit|sniff|ambiguous|none", "glossary_candidates": [...], "changes": "<用户手写>", "changes_file": "CHANGES.md" | null, "changes_source": "explicit|sniff|ambiguous|none", "changes_candidates": [...], "tech": "<用户手写>", "tech_file": "TECH.md" | null, "tech_source": "explicit|sniff|ambiguous|none", "tech_candidates": [...], "updated_at": "YYYY-MM-DD HH:MM"}`
  - 三组字段（`glossary*` / `changes*` / `tech*`）各自独立、结构完全同构；`glossary` 那一组是 v1.3 既有形态，后两组是 v1.6 起。
  - 每个 `*`（用户手写指定项）渲染器只读、不覆盖；其余字段每轮重写。
  - `glossary_file` 是真实文件名，没有术语表时为 `null`；`glossary_source` 取 `explicit`（用户指定）/ `sniff`（内容嗅探唯一命中）/ `ambiguous`（多个候选、没指定）/ `none`（没有术语表）；`glossary_candidates` 仅歧义时非空。
  - 歧义时 AI 在对话里问用户一次，拿到答案后写回 `glossary` 字段即可，`glossary_source` 下一轮自动变成 `explicit`。
- 采集器整段排除 `dev-dashboard/` 自身，以上机器文件与 `.versions/` 永远不会变成变更事实。

### 同步链路 5 项改进（**批 4 已实现**）

> 这一节现在是**现状**（批 4 落地，2026-10-12）。落地前它是设计规格；实现者按契约而非施工图实现，并在实测中发现施工图错了一处（见第 1 条的"合并起点"）。

1. **`.facts.json` 停止单调增长**：collect 时把**已被证据引用**的项**出列**（旧行为只按 `.dashboard-ignore` 过滤，采集过的事实会永久留在文件里、每轮重新合并比对）。
   - **为什么**：`.facts.json` 语义是"累计**未归置**集合"。已归置的项留着只会让它无限膨胀，每轮 merge 成本与文件长度同增，文件越大越容易写出半截 JSON —— 而 `corrupt` 是 blocker，等于自己制造翻车面。
   - **为什么不影响覆盖性审计**：审计判据是「**本轮**采集到的事实要么被证据引用、要么被显式忽略」（`pending = 事实 ∖ (证据 ∪ ignore)`）。**已归置 ≠ 丢失**：出列的项此前已经过同一判据、被证据接住；它们消失只说明"这轮没有未归置项"，blocker 语义不变。`change: deleted` 的删除事件同样按此出列（时间线记一笔后就不必再留）。
   - **合并起点 = 上一轮 `.facts.json` 本身，不是空 dict（implemented，有据偏离施工图）**：collect 的 `merged` 必须从**上一轮 `.facts.json` 的 `items`** 起手，再并入本轮新采集项，最后一起按（证据 ∪ ignore）过滤。**为什么**：`.facts.json` 是**唯一**的"累计未归置集合"，上一轮没归置的项必须留到这一轮继续被审计；若照施工图那样"空 dict 起手、只并入本轮"，**连跑两次采集再渲染会把覆盖性门禁洗掉**（实测：变体做法 → `facts` 变空、`render` 退 **0**；按契约做法 → 仍退 **2**）。**改回空 dict = 让 blocker 失效，这一条不许回退。**
2. **`.state.json` 去重**：只保留 `last_collect` 与 `files`，**删掉 `pending_items` 拷贝**（旧文件里的该键兼容读后直接忽略）。
   - **为什么**：`pending_items` 是 `.facts.json` 的第二份拷贝，既重复又要两处同步；更糟的是旧 collect 的合并方向是**先读 `state.pending_items`、再由新采集覆盖** —— `.facts.json` 被人工校正或按第 1 条出列后，旧的 `state.pending_items` 会把它们**复活**，形成"state 压过 facts"的第二事实源。去重后 `.state.json` 只记采集游标，累计未归置集合的唯一事实源是 `.facts.json` 自己。
3. **`last_collect` 丢失保护**：`.state.json` 缺失、或 `last_collect` 是 1970 / 不可解析时，**限制 git 采集窗口**（最近 30 天，或最多 500 条，取先到者）并给一条 WARN，而不是从 1970 全量扫。
   - **为什么**：旧行为"缺失即从 1970 开始"。**重新克隆仓库**（新 `.state.json` 不存在）会让 git log 吐出全历史 → 全部变成未归置事实 → 一次全量 blocker，用户面对几千条无从下手。限窗 + WARN 把灾难变成"采最近一段并明确告知历史未采全"。
   - **已知限制（不修，记下来免得被当 bug）**：`last_collect` 只存到**微秒**，而 NTFS mtime 有 **100ns** 分辨率 → **同一微秒内先写文件再采集**，该文件会**每轮都被判 `modified`**（实测 `mtime - since = 2.4e-7`）。真实节奏（两次动作间隔 ≥ 毫秒级）不触发。**要修它就得把游标精度写进 `.state.json` = 动契约字段**，因此按"一次契约变更"处理，不许当 bug 随手改。
4. **prune 策略**：`.versions/` 默认**保留最近 20 版**（`snapshot_version.py prune [--keep N]`，超出从最旧删起，`index.json` 同步收缩，`n` 不回退不复用）；`.inbox.jsonl` 收取后**截断为空文件**（不是删除文件）。
   - **为什么是 20 版**：每版只存几份 Markdown（KB 级），20 版足够覆盖日常节奏并留出回退纵深；更早的历史交给 git —— Markdown 本来就在版本控制里，快照不该当归档用。
   - **为什么截断而不是删文件**：面板与渲染器以"文件是否存在"判断数据源（`inbox_pending` 三态）；删文件会把"待生效 0"变成"缺数据"，截断保持文件在位、语义不变。
5. **写前快照 + git 干净检查**：每次 update **开始前**先 `snapshot_version.py preflight`（查 `git status --porcelain`，脏 → **退 3** 并列出文件，问用户 commit / stash / 继续，不许静默继续），再 `snapshot_version.py save --note "更新前自动快照"` 存一版（旧行为只在拍板落定时存）。
   - **为什么写前快照**：只有"拍板落定"一个快照时机时，update 中途把 Markdown 改坏就没有任何可回退基点，而 `.versions/` 本来就是为回退准备的。
   - **为什么查 git**：写入必须以 git 为记录 —— 这次改动是谁改的、改前长什么样，只有提交历史能回答。工作区脏着改，快照与 diff 都失去基线；问一次比事后无法归因便宜。
   - **非 git 工作区**：preflight **退 0** 并打印"无 git，跳过检查"（**降级要说话**，不算通过）。

## 版本快照（.versions/，v1.3 起）

- 布局：`dev-dashboard/.versions/index.json` + 每版一个目录 `NNN-<yyyymmdd-HHMM>/`（内含当时 `dev-dashboard/*.md` 的拷贝：三份事实源 + 术语表 +（v1.6 起）变更规则与技术地图，叫什么名字就按什么名字存）。
- `index.json`：`{"versions": [{"n": 1, "dir": "001-20261008-1405", "created_at": "ISO8601", "note": "一句话说明"}]}`，新的在后，`n` 递增不复用。
- 由 `scripts/snapshot_version.py` 创建（拍板落定后 skill 自动存一份；用户说"存个版本"时带说明存一份）。人手勿改。
- 快照不含 `index.html`（机器产物，可随时由 Markdown 重新导出）。
- **快照是"上一轮"的权威载体**（v1.6）：技术地图的「原有模块证据全消失」漂移检查**唯一**依据 `.versions/` 里最近一份 `TECH.md` 快照（见「TECH.md · 审计与 WARN」）——因此**快照必须含 `TECH.md` / `CHANGES.md`**（文件名按实际）。**只读、不改写、不新增状态文件**；拿不到快照就 fail-closed（不产那条 WARN）。

## 升级与兼容（机器文件与事实源，**v1.6 补录**）

> 这一节回答三个问题：**插件换版本/升级时，`dev-dashboard/` 里什么能变、什么绝不能变？** **跨版本读不动怎么办？** **用户重构项目时，我们怎么不静默显示过时的图？**
> 每条都标 **【已实现】/【目标形态】**——不许把目标形态当现状读。

### 一、产物四类清单 + 每类的升级契约

| 类 | 文件 | 谁写 | 升级时**允许** | 升级时**绝不允许** |
|---|---|---|---|---|
| **A 用户事实源** | `PRODUCT.md` / `FEATURES.md` / `NOW.md` / 术语表 / `CHANGES.md` / `TECH.md` | **AI 在对话里写**（脚本只读，见下） | 只换**读法**（解析器、界面、WARN）；**内容迁移**必须 AI 先提出 → 用户同意 → **写前快照** → 再改 | **覆盖 / 重写 / 删除**；静默补字段；因"版本不匹配"清空或重建 |
| **B 机器产物** | `index.html` / `.cyd.json` / `.facts.json` / `.state.json` | 脚本 | 整份重生成；**schema 变更只新增字段、不改既有字段语义**；旧键兼容读后忽略（`pending_items` 即范例） | 当成第二事实源；重建时丢掉"累计未归置事实" |
| **C 用户配置** | `.dashboard-ignore` | 用户手写 | **只能**在语义变更时给出**检测 + WARN + 改写建议**（见 §三·3） | 覆盖、追加、规范化用户条目 |
| **D 用户资产（回退基点）** | `.versions/`（+`index.json`） | 脚本 | **只追加**；`prune` 只按**数量**删最旧 | 迁移 / 重排 / 改名 / 清空；改变目录命名（老快照必须**永远**可 `diff`） |

**为什么 `.versions/` 单列一类**：它**不可重建**（事实源只保留当下，历史只在快照与 git 里）。把它当"机器产物"随手重建 = 丢掉用户唯一的回退基点。

**脚本不写 A 类的机械证据**【已实现】：`collect_facts.py` / `render_dashboard.py` / `snapshot_version.py` **对 A 类只读**（`collect_facts.py` 里出现的写 `.md` 全在 `self_test()` 的临时目录内）。所以"升级覆盖用户事实源"的**唯一可能通道是 AI 的写入行为**——这由 §二 的三条硬规则约束。

### 二、升级安全的硬规则（三条）

1. **升级只换读法与画法，不换内容**：插件升级 = 解析器 / 渲染 / 门禁的变更；**A 类内容零改动**。【已实现】（脚本只读 + 契约）
2. **任何写前快照 + git 干净检查**【已实现，批 4】：`snapshot_version.py preflight`（脏 → **退 3** 并列出文件，问 commit / stash / 继续）+ `save --note "更新前自动快照"`；非 git 工作区**退 0 并打印"无 git，跳过检查"**（降级要说话）。
3. **B 类必须可从 A 类重建**【已实现】：删掉 `index.html` / `.cyd.json` / `.facts.json` / `.state.json` 后重跑 `render` + `collect`，界面应回到同一状态（差异仅 `updated_at` / 采集窗口）。**这条是"机器产物"这个身份的定义**——做不到就不是机器产物。

### 三、跨版本兼容与信息丢失

#### 1. 版本位**分三件**，不要一个 `version` 顶全部

| 位 | 含义 | 现状 |
|---|---|---|
| **机器文件 schema** | `.cyd.json.version`（`1`）、机器文件各自的字段布局 | **【已实现】**：`.cyd.json` 有 `version: 1` 且**每轮重写时保留未知键、不覆盖用户手写的 `glossary` / `changes` / `tech`** |
| **事实源格式版本** | "这批 Markdown 按第几版契约写"（决定旧插件能不能安全回写） | **【目标形态】**：`.cyd.json` 增 `format: <int>`；A 类文件可选标记 `<!-- cyd-format: N -->`（**只加一行注释，不改正文**）。**判据两条（同族 fail-closed；**逐字文案归 `references/copy-deck.md` §16.6 的两行（契约不内联中文）**——A、B 各自一行）**：**A「超前」**= `format > 本插件支持` ⇒ **只读、不写回** + 产一条 WARN；**B「非法」**= `format` **存在但不是整数（含布尔）** ⇒ **只读、不写回** + 产**另一条** WARN；**缺失 ⇒ 视为 `1`**——那是**向后兼容的正常情况，不产 WARN**。**A 与 B 互斥**（"比插件新" vs "读不出来"）：**实现必须保证两者不会同时产**，并**有断言**（同一个 `format` 值不可能既超前又不可解析）。**fail-closed 只落在渲染器侧**（见下「写者唯一性」）。 |
| **写入者版本** | "这个项目最后被哪个插件版本写过" | **【目标形态】**：`.cyd.json` 增 `writer: {skill: "<semver>", at: "<ISO8601>", copy: "<副本标识>"}`（版本号取 `manifest.yaml` 的 `version`）。**版本冲突的判据只看 `writer.skill`，不看 `at`**——`at` 每次真写都变，拿它进两端比对会**假红**；`at` 只供人看。 |

**结论**：**一个 `version` 不够**——它现在只描述机器文件自己的字段布局，既不表达"事实源能读到哪一版"，也不表达"谁写的"。**最小动作**是把上面三件补齐（都落在 `.cyd.json`，**不新增文件**）。

**写者唯一性（v1.6 补录，先读这条再谈"只读"）**：
- **本项目的机器文件（`.cyd.json` 等）只由渲染器写**（`render_dashboard.py:write_cyd_meta`，每轮重写）；**面板与共享核只读**——实证：`plugins/dsh-plugin-control-your-development/src/client.src.js:136` 用 `readOpt` 读 `.cyd.json`、`:155` 把 `metaRaw` **只读**传给共享核、`:328` 写的是 `verifyWrite: null`（注释原文："写回走 notify（steer/信箱），面板不直接改文件"）；共享核 `dashboard.core.js` 全文**没有任何文件写入动作**（唯一 `write*` 是 `navigator.clipboard.writeText`，那是剪贴板）。
- ⇒ **fail-closed（`format` 超前 ⇒ 只读、不写回）只落在渲染器这一侧**；**共享核的职责是产出同一条 WARN**（让用户看得见 + 供 `dual_parser_diff.py` 逐条比对），**不是执行"不写回"**——它**根本没有写回动作**，让它"别写"是给不存在的对象加保护。
- ⇒ **`notify`（steer / 信箱）不属于写回**：那是**面板把用户意图作为一条消息发给 AI**，改文件的是 AI，不是面板；因此"面板只读"与"用户能改看板"同时成立，不矛盾。
- **理由（依据）**：**"只读"这个词必须先问"谁是写者"**——写者唯一时，**保护只落在写者那一端**，其它端只需要**说出同一件事**。否则会掉进两种坏结果之一：**去实现一个不存在对象的保护**（空转），或**在错误的端做拦截**（与写者打架）。

**「保留未知键」的适用范围与边界（v1.6 补录）**【**已实现**】：
- **范围 = 三件机器文件都适用**：`.cyd.json`（`render_dashboard.py:write_cyd_meta`——**整体读入后只覆盖已知键**）、`.facts.json` 与 `.state.json`（`collect_facts.py` 的 **`_preserved()`**，用于 `:357` / `:364` 两处写入）。**证据来源就是这两处实现**，不是"将来要这样做"。
- **边界（最容易被误读成"整份不动"）：保留未知键 ≠ 冻结整文件**——**已知键照旧更新**（`.facts.json` 的 `generated_at` / `source` / `items`、`.state.json` 的 `last_collect` / `files`、`.cyd.json` 的 `version` / `glossary_*` / `updated_at` 都按本轮重写）。**"保留"只针对不认识/不属于本版的键。**
- **唯一例外：已知的**废弃键必须丢**（`pending_items`）**——留着会把 `.facts.json` 的第二份拷贝"复活"，单一事实源当场就破（`collect_facts.py:205-207` 明确排除它）。⇒ **"保留未知键"保护的是"别人写的键"，不是"本版已废除的键"。**
- **为什么这条必须写清、不能只靠读代码**：旧读法（"`set(state) == {"last_collect","files"}`"）**真的产出过一条自检断言**，照它实现就会**把他人写的键再清一遍**。所以措辞必须把**"本版只*写*这两个键"**与**"这份文件只能有这两个键"**明确分开。

#### 2. 旧事实源在新插件下读不动 → 降级 + WARN（复用现有 `warnings` 体系）

- **缺字段**（旧文件缺 `- 证据:` / 缺 `### 子项` / 旧两态决策 / 旧 `.state.json` 的 `pending_items`）：**照常解析 + 按默认值降级**，**不报错**。【已实现】——`warnings` 已有"缺状态字段 / 缺简介 / 缺 `层:` / 缺 `职责:`"等条目，且契约明令**旧两态不得因缺三态报 WARN**。
- **出现本版本不认识的写法**：**【目标形态】** 归入 `warnings` 的新一类 **`format_*`**（例如 `format_newer`），与既有 WARN 同管道（进审计弹层「其他提示」、不进 `ok`、两端逐字同文案）。**判据**优先用显式 `format` 标记，**不靠猜字段名**（猜字段名会把用户的普通文本误判成新语法）。

#### 3. `.dashboard-ignore` 的**破坏性语义变更**（现成的坑，必须给检测）🔴

契约「`.dashboard-ignore`」一节自己写着：**旧版 `fnmatch`（Windows 大小写不敏感、支持字符类）→ 新版 glob**，"若你的 ignore 依赖过这类写法，升级后要改写（例如 `Tests/*` 改成 `tests/*`）"。
**问题**：这句话**只在文档里**——升级后用户那些条目**静默失效**，事实源重新变"未归置"，用户只看到一堆莫名其妙的 blocker，**没有任何一条提示告诉他"是你的 ignore 写法过时了"**。

**判据（唯一成文处在这里；逐字文案归 `references/copy-deck.md` §16.6）**【目标形态，实现待落地】：
- **参照集合** = **本轮 `.facts.json` 的 `items[].path`**（本轮未归置事实路径；**用真实路径比对，不猜用户意图**）。
- **旧语义参照匹配器** = `fnmatch.fnmatchcase(p.lower(), pat.lower())` —— 一次性把旧版的三处差异都建模进来：`*` / `?` **跨 `/`**、**大小写不敏感**、**支持 `[seq]` 字符类**。
- **判据**：**存在**一条参照路径 `p` 使「旧语义参照命中」为真、而「新语义 `glob_match(p, pat)`」为假 ⇒ 该条计入**失效条目**。（两边都命中 = 这条规则本来正常工作 → **不报**；两边都不命中 = 惰性模式 → **不报**，避免误报。）
- **这条判据覆盖的失效类**（三类的公共形态都是"旧版会命中、新版不会"）：
  ① **字符类** `[`…`]`（新版按字面处理 → 基本永不命中）；
  ② **大小写与实际路径不符**（新版大小写敏感；旧版在 Windows 上不敏感才对得上）；
  ③ **依赖通配符跨目录**（旧版 `*` / `?` 能吃掉 `/`）：`*.log` 旧版能命中 `dist/app.log`、新版**只命中根目录**；`build/*` 旧版命中 `build/a/b.js`、新版**只命中一层**；`a?b` 旧版可跨目录、新版只在段内。**契约举的例子 `*.log` 正属这一类**，最危险。
  - **不列入判据**：`!` 取反 —— 旧版 `fnmatch` **也不支持**，它从来就没生效过，不属于"升级后失效"（列进来会误报）。
- **一条 WARN 覆盖全部失效条目**（不是一条一个）：`X` = **首个失效条目原文**（用户一眼认得出是哪一行），`N` = 失效条目总数；**可选加分**：工具的 `title` 里列**全部**失效条目（"正文给首个 + 总数、悬停给全部"，不占正文长度）。**只提醒、不改用户文件**。
- **作用域 = 两端（不标 `共享核`）**：**为什么**——ignore 的解析与匹配**两端各有一份**（Python `collect_facts.py:_load_ignore` + `render_dashboard.py:glob_match`；共享核 `dashboard.core.js` 的 `globMatch` + `assembleData` 里的 ignore 分支），且这条 WARN 进 `warnings[]` 要**逐条比对**，所以判据必须在**两端**都实现、且逐字同文案。
- **文案**：逐字文案归 `references/copy-deck.md` §16.6（契约不内联中文）。

#### 3.5 凡"升级会让用户配置/数据语义改变"的地方，都必须有**用户可见 WARN**

- **口径（v1.6 补录）**：任何会让**用户既有配置或数据的语义**发生变化的改动（ignore 写法、字段含义、机器文件布局、枚举取值…），**必须**配一条**用户可见的 WARN**，**不许只在契约/文档里写一句"升级后要改写"**。
- **实现要求**：该 WARN 的**判据两端都要实现**（`warnings[]` 要逐条比对，单端实现会造成跨端漂移）；**判据归契约、逐字文案归 `references/copy-deck.md` §16.6**；**作用域按行内标记判**（两端都要产的，**不标 `共享核`**）。
- **为什么**：文档只有"读契约的人"看得见，**用户看不见**；只写文档等于**把一次静默失效留给用户自己发现**。

#### 4. `.state.json` / `.versions/` 的向前兼容

- `.state.json`：**【已实现】** 只记 `{last_collect, files}`；旧 `pending_items` **兼容读后忽略**；**今后只允许新增键**（新增键不得改变既有键语义）。
- `.versions/`：**【已实现】** 布局稳定（`NNN-<yyyymmdd-HHMM>/` + `index.json`）、`n` 递增不复用、`prune` 只按数量删最旧。**【目标形态】** 补一条**门禁级回归**：拿一份"三版之前"的旧 `.versions/` 夹具，断言 `snapshot_version.py list` / `diff` 仍可用（否则布局变更会在无人知晓时砸掉回退能力）。
- **信息不丢的原则**：不兼容时**只新增目录/键、不迁移旧目录**——旧快照永久只读可查。

#### 5. "版本冲突"的三种具体形态 + 检测手段

| 形态 | 场景 | 后果 | 检测手段 |
|---|---|---|---|
| **① 回退用旧版插件**（同一项目先被新插件写、又被旧插件写） | 多台机器 / 手动降级 / 两份副本一老一新 | 旧解析器**不认识的字段被静默丢掉** | **判据口径（不变）**：`writer.skill` 与当前 `manifest.yaml` 版本比对，`writer > 当前` → 产 WARN。**写侧【已实现】**：`.facts.json` / `.state.json` **现在都写入 `writer: {skill, at}`**——`collect_facts.py:362`（构造）/ `:365`（`.facts.json`）/ `:372`（`.state.json`），版本号**复用渲染器那一份** `_skill_version()`（`:38` 导入 ⇒ 单一执行路径）；实测键 = `.facts.json` `['generated_at','items','source','writer']`、`.state.json` `['files','last_collect','writer']`；self-test 已固化（`:526-533`：`writer.skill` 必须等于本插件版本）。**判据侧【目标形态，未扩展】**：形态①的**检测仍只在 `.cyd.json` 上生效**。**为什么现在不扩**：② `.state.json` **读侧做不到两端**——宿主读的那一组文件里**不含 `.state.json`**（`client.src.js:130-227`），面板也不消费它 ⇒ 要两端**必须先改宿主**；③ `.facts.json` **可以两端**，但**文案不能复用**（现有那句点名了 `.cyd.json`）⇒ 需在 deck 新开一句。⇒ 这属于"**为一个当前没有用户可见需求的扩展去改契约**" ⇒ **本轮不做**。**一句话结论：字段已写、判据未用**——**别以为这条 WARN 已经覆盖那两个文件**。（"写机器文件必须保留未知键"另见下「保留未知键」的适用范围。） |
| **② 事实源格式版本不匹配** | 用户从别人那里拷来较新的 `dev-dashboard/` | 同上，且**是用户内容，风险更高** | **【目标形态】** §三·1 的 `format` 标记 → 只读 + WARN |
| **③ 两份插件副本并存 / 并发写** | 插件包副本与全局安装副本各有宿主 | 两个宿主各写同一份机器文件，**后写者覆盖前写者** | **【目标形态】** ① `writer` 里带**宿主副本标识**（哪个副本写的）；② **乐观并发检查**：写机器文件前比对"读取时的 mtime/内容哈希"与"此刻的"，不同 → WARN「文件在你读它之后被改过，已重新读取」并**重算**（last-writer-wins 的风险**可见化**）。注：`verify_status.py` 的三副本漂移检查管的是 **skill 副本自身**，不覆盖这一条 |

### 四、用户重构项目时的准确体现（拆分 / 合并 / 改名 / 搬迁）

**能自动反映的（证据路径变化）**【已实现】：`证据` 路径存在性 → `health.matrix` / `evidence_missing` / `evidence_invalid`（**技术地图的模块证据同样进矩阵**，owner 记作 `技术地图 / <模块>`）；`declared_refs`（`changes_only` / `tech_only`）、两类漂移检查（`changes_drift` / `tech_drift`）、>10 条 WARN。

**必须靠人 / 靠 AI 重写声明**：`FEATURES.md` 的功能定义（合并/拆分后"一个功能"的边界变了）、`TECH.md` 的**模块边界**与 `层` / `职责`（新架构不是旧架构的重命名）、`CHANGES.md` 的规则归属。**这些不能自动推断**——`TECH.md` 的保真红线就是"绝不做代码解析"，不能靠读 import 猜出新架构。

**"技术地图已经跟不上了"的可检测信号（关键）**——三级，逐级加强：

| 级 | 信号（判据可机检） | 现状 |
|---|---|---|
| **S1 全灭** | 某模块的 `证据` 路径**一条都不存在** → 该模块大概率被删/被搬 | **【已实现】**（`tech_drift` ②：与 `.versions/` 最近一份 `TECH.md` 快照对比；无快照 → fail-closed 不产）；另有"有模块但全部证据为空"一条 |
| **S2 新目录** | 顶层目录**没有任何模块覆盖它** | **【已实现】**（`tech_drift` ③，只用本轮 `.facts.json` + 本轮 `TECH.md`） |
| **S3 部分失效（缺口最大）** | 模块**部分**证据不存在（`>0` 且未全灭）→ 地图**一半对一半错**，最容易被信 | **【目标形态，最小实现】按模块算 `证据存在率`**：`0 < 失效率` 的模块 → 计入 `tech_stale.modules`（列表）+ `tech_stale.ratio`；**渲染三处**：技术视图图例下一条 `.snote`「**技术地图有 N 个模块的证据已经找不到了，可能跟不上了**」、审计弹层固定行、`TECH.md` 侧的状态徽标。**为什么单列一条**：S1 只在"全灭"时响，而重构最常见的是**部分搬迁**——那时 S1 安静、用户看到一张"看起来正常"的错图 |
| **S4 搬迁/改名（可增强）** | 本轮 `.facts.json` 里 `change: deleted` 的路径 **∩** 某模块/功能的证据路径 ≠ ∅ | **【目标形态，P2】** WARN「你删除/移动了 `<路径>`，它仍是技术地图里模块 `M` 的证据——是搬走了还是真删了？」（`.facts.json` 的累计语义天然带着最近窗口内的删除事件） |

**可见性原则**：**陈旧必须比正确更显眼**——新技术视图若 `tech_stale` 非空，标题旁给 **`⚠`**、图例下给 `.snote`、审计弹层给一行；**不许**只在用户点开审计时才看到。

## `--workspace` 参数

渲染器与采集器默认这样推断工作区根：从 `dev-dashboard` 的父目录向上找 `.git`，找不到就以 `dev-dashboard` 的父目录为根。以下两种情况**必须显式指定**，否则证据路径会被判成不存在：

- `dev-dashboard/` 不在项目根（例如放在 `docs/dev-dashboard/`）；
- monorepo：`.git` 在外层仓库根，而实际工作区是子目录（例如 `apps/web/`）。

```
<Python解释器> <skill目录>/scripts/render_dashboard.py <dev-dashboard目录> --workspace <工作区根>
<Python解释器> <skill目录>/scripts/collect_facts.py <dev-dashboard目录> --workspace <工作区根>
```

两端必须一致：采集时用了 `--workspace`，渲染时也要用同一个，否则 `.facts.json` 里的路径对不上。

## health 字段清单

`index.html` 内嵌数据里的 `health` 是掌控条「数据健康」徽章与审计弹层的数据源（Python 渲染与网页内刷新两端字段一致）：

- `ok`：本轮全绿（无失效/越界证据、无未归置事实、`.facts.json` 未损坏、无缺验证记录的「已验证」）。
- `matrix`：证据矩阵，每条含 `path` / `owners`（归属功能或"使用流程"/"时间线"）/ `kind` / `exists`。
- `evidence_missing`：在工作区里找不到的路径列表。
- `evidence_invalid`：违反「证据路径红线」的路径列表。
- `facts_pending`：未归置的变更事实条数。
- `facts_error`：`""`（正常）/ `"missing"`（还没采集）/ `"corrupt"`（损坏，不可审计）。
- `verify_missing`：标了「已验证」却没有验证记录的功能名列表。
- `inbox_pending`（v1.5 起）：`.inbox.jsonl` 里**尚未收取**的行数，即掌控条 `⏳ 待生效 N 条` 的数据源，**以文件为准**（不做本地持久化增量）。三态：非负整数 = 读到（文件不存在或为空时为 `0`）；`null` = 读取失败（IO／权限），界面显示 `—`；`undefined` = 该宿主**没提供这个数据源**（只有网页内刷新路径如此），不渲染徽章——**别按"是不是离线页"判断**：Python 导出的 index.html 内嵌的是导出时刻的真实值，属第一种。**不参与 `ok` 计算**；单行 JSON 解析失败时跳过该行、给 WARN（**读取失败本身不写 `warnings[]`**，见「机器文件」一节）、不阻断。JS 侧同一口径见 `assembleData`（`templates/dashboard.core.js`），两端必须一致（dual_parser_diff 门禁）。
- `inbox_items`（**v1.5 补录**，与 `facts_generated_at` 同类，不另起版本）：`.inbox.jsonl` 里未收取行的**逐条内容**，供 `⏳` 徽章点开的明细浮层用（用户要求"点开列出是哪几条"）。每条 **`{type, text, ts}`**（`ts` 就是 host 写进 `.inbox.jsonl` 的原始时间戳字段，见「机器文件」一节的三字段定义；明细浮层的「时间」列取它），`type` 取值集合沿用契约的四个（`decide` / `verify` / `command` / `ask`）。**三个字段都做同款守卫**：`type` / `text` / `ts` 不是字符串一律归一成**空串**（与 `facts_generated_at` 同款——不猜、不转换、不编造时间）。**降级与 `inbox_pending` 同口径、同一次读取**：文件不存在或为空 → `[]`；坏行跳过 + WARN（**一行一条 WARN，不汇总**，与 `inbox_pending` 同口径）；**读取失败 → `null`（不是 `[]`）——"读不到"与"没有"必须可区分**，界面据此显示"读不到待生效记录"而不是"0 条"。**不参与 `ok`**。**不得为它做第二次文件读取**：JS 侧从同一个 `parts.inboxRaw` 解析（同源），Python 侧复用同一段已读文本——两次读取会造出"计数与明细不一致"的第二事实源。
- `facts`：`.facts.json` 里每条事实的 `path` / `kind` / `change` / `pending`。
- `ignore`：`.dashboard-ignore` 生效的 glob（已剔除 `#` 注释行与空行）。
- `source`：本轮变更事实的采集来源（`git` 或 mtime 说明，取自 `.facts.json` 的 `source`），网页据此显示"变更来自 git 还是文件时间"；旧 `.facts.json` 没有该字段时为空串。
- `facts_generated_at`（v1.5 起）：**"上次采集是什么时候"的原始串**。口径拆两层，别混：
  - **字段层（原样透出，不做日期校验）**：`.facts.json` 存在且是合法 JSON、顶层有 `generated_at`、且它的值是**字符串** → 该字符串**逐字透出**（哪怕值不是合法日期，例如 `"not-a-date"`，也照原样给）。只有这三种情况取**空串 `""`**：文件不存在、JSON 不可解析、缺键或值不是字符串（含 `null` / 数字 / 对象）。旧 `.facts.json` 没有该键时同样空串。不许编造时间、不许用 `null` 代替空串。
  - **口径说明**：字段层只负责"原样透出"，**日期合法性一律在显示层判断**——Python 侧只给串，JS 侧只在前端算相对时间，两端都不在字段层做日期校验（否则会把合法但格式少见的串误杀成空）。
  - **不参与 `ok` 计算**（没采集过 ≠ 不健康）。与 JS `assembleData`（`templates/dashboard.core.js`）同口径，**且不在 `dual_parser_diff.py` 的归一化剔除列表里**——该脚本只剔 `workspace_uri` / `updated_at` / `health.matrix`，本字段要真比对（因此非法值也要两端一致地透出）。显示层消费见「界面文案」的 `⏱ 上次采集` 与审计弹层「上次采集：」。
- `warnings`：非致命提示（非法状态、缺简介、重名、依赖环、已定选项与选项对不上、子项写了依赖、术语表解析异常、术语表歧义、用词漂移、声明类文件漂移等）。
  - **文案归属总则（补录、不升版）**：`warnings[]` 是 `dual_parser_diff.py` **逐条比对**的字段，因此**每一条 WARN 的逐字文案归 `references/copy-deck.md` §16.6（契约不内联中文）、且只允许存在这一处**；**契约只钉两件事：① 触发条件（判据）② 两端必须逐字同文案**。契约里再内联一遍中文 = 第二份事实源，两端各抄一份必然漂移（执行者按笼统契约改错位置、契约落后实现一个字段，这两次亏都出在这类重复上）。
  - **为什么没有例外**：WARN 的**判据都在触发条件里**（都是可机检的条件，例如"状态值不在五态内""模块数 > 0 且证据全空"），那句中文只是**呈现**。因此**不设"文案承担判定职责"的例外**——一开口子，后面每条 WARN 都能自称判据。
  - **两道门禁互补，缺一不可**：**逐字文案归 `references/copy-deck.md` §16.6（契约不内联中文）**；每条 WARN 由**常驻门禁 `plugins/control-your-development/smoke/warn_copy_check.py`** 逐条核对**两端实现里有没有这段话（静态，随冒烟一起跑）**；**运行时**两端 `warnings[]` 的**逐条比对**仍由 `dual_parser_diff.py` 负责。**分工**：静态门禁拦"根本没写／只写了一端"，运行时门禁拦"写歪了／触发条件不一致"。任一道红了都不许绕过。
  - **§16.6 的登记格式（输入契约，写新 WARN 前必读）**：静态门禁**按「依据列含 `本节定稿`」挑行**、**按「汉字锚点 ≥2 连字」比对**；`<…>` 占位与 **≥3 项 `/` 枚举值表**视为占位。因此：**新增 WARN 必须照这个格式登记，否则门禁看不见它**；反过来，**把定稿的字面文本塞进 `<…>`、或写成 ≥3 项 `/` 列表，会让该段不再逐字受检**（等于自己把这段移出门禁覆盖）。这两句是"怎么写文档才受保护"的规则，不是建议。
  - 逐条判据、两端内联位置与现文案见 `output/WARN文案清单.md`（一次性核对产物，不入库；**常驻依据是 §16.6 + `warn_copy_check.py`**）。
- `glossary_drift`（v1.3）：用词漂移明细，每条含 `alias` / `term`（标准用词）/ `file` / `count`。

- `changes_status` / `tech_status`（v1.6 起）：变更规则与技术地图的识别结论，结构与 `glossary_status` **完全同构**（`{file, source, candidates}`），同源于 `.cyd.json` 的 `changes*` / `tech*` 两组；`source` 同为 `explicit` / `sniff` / `ambiguous` / `none`。
- `declared_refs`（v1.6 起）：**仅由声明类文件引用的路径/条目**——`{changes_only: [声明条目], tech_only: [具体路径]}`。**两边单位不同，别混用**：`changes_only` 的元素是 CHANGES.md 的**声明条目**（可能是 glob，如 `src/pages/**`）；`tech_only` 的元素是 TECH.md 模块证据里的**具体路径**。判定口径：`changes_only` 用 **glob 匹配**（声明条目匹配不到任何"已被功能／使用流程／时间线引用"的路径 → 计入；匹配到 → 不计入），`tech_only` 用**路径成员判断**（该路径没有被上面三类引用 → 计入）。审计弹层固定分两行渲染：`仅由变更规则声明的路径：N 条`（单位=声明条目）与 `**仅由技术地图引用的文件：N 个**`（单位=具体路径）。**不计入 `ok`**；任一类超过 10 条时给一条 WARN（防后门的可见性防线，理由与两条标签的措辞见「CHANGES.md」一节）。

- **这份形状是契约规定的，不是"靠差分互相约束"**：`dual_parser_diff.py` 只能发现**当下**两端不一致；**两端同时改名照样全绿**——"门禁能约束"≠"契约规定过"。字段名以本段为准。
- `path` **允许 glob**（如 `tests/**`），语义与 `.dashboard-ignore` 同款（`*` 不跨目录、`**` 跨目录、`?` 单字符、大小写敏感）；`owner` 指向功能/模块名（对不上 → 走声明类文件的漂移 WARN）。
- `action` 是**自由文本的归置方式**（如"忽略""记进时间线"），**机器只用"这条路径被声明过"这一事实，不解释 `action` 的语义**——给它定枚举就等于替用户猜语义（保真红线）。真要枚举化，另开契约变更。
- **`evidence` 保持"路径字符串数组"，不重复一份 `exists`**：存在性判定统一走 `health.matrix`（每条证据都有 `path` / `owners` / `kind` / `exists`，模块证据同样进矩阵），**不在模块里造第二份真相**。
- **`links` 是内嵌的、不是顶层边表**（一条边归声明它的模块所有）：需要边列表时由**渲染核现场拍平**（`from = 模块名`、`to = link.name`、`label = link.rel`），**拍平只允许一处实现**；`graph-visuals.md` §F2 里那份 `DATA.tech.edges` 示例应理解为这个派生视图（该文件已声明"字段名以契约为准"）。
- 指向不存在 / 已废弃模块的 `link` 由视觉侧按 `graph-visuals.md` §B 画成幽灵边（不报错）。
- 顶层 `changes_file` / `tech_file`：真实文件名（`null` = 没有）。

顶层 `decisions`（v1.5 起字段固定为六项）：每条 `{id, title, decided, options, multi, obsolete}`——`decided` 仍是空串或规格化后的选项串（如 `A、C`）；`multi` 只是**提示语**标志（见「NOW.md · 决策」）；`obsolete: true` = `已废弃`，旧的两态文件恒为 `false`。顶层 `todos`：`[{done, text}]`，结构 v1.5 未变。
