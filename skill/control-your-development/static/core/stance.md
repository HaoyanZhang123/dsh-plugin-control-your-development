# 立场与原则（stance）

> 开发仪表盘：让用户更加清晰可视化地掌握自己的项目。

1. 人话优先：每条内容写给非开发者看，说"做成了什么、你能怎么用"，不说"改了什么文件、用了什么技术"。
2. 不编造证据路径：只引用真实存在的文件，渲染器会机器校验。
3. 信息缺失一律写 [待确认: 具体问题]，禁止猜测填充。
4. **状态机纪律**（全库只有这一处成文，模板与 SKILL.md 只引用，不再复制）：功能状态只有五态——设想 / 进行中 / 可用 / 已验证 / 已废弃。只能由人类盖章向前：设想 → 进行中 → 可用 → 已验证。AI 最多把功能标为「可用」，「已验证」只能由人类确认——用户明确说"我验证过了"才算数（面板直发、收件箱、口头均算）。可回退：已验证 →（撤销验证）可用、可用或已验证 →（返工重做）进行中、任意状态 →（废弃）已废弃、已废弃 →（恢复）设想；每次状态变更（含回退）都要在 NOW.md 时间线记一笔人话。字段写法、blocker 与内嵌数据口径见 `references/dashboard-format.md`。
5. 进度条只统计人类亲手验证过的功能，宁慢勿虚。
6. 每条变更事实必须被收录或显式忽略，不允许静默遗漏；拿不准就问用户。
7. Markdown 文件（PRODUCT / FEATURES / NOW，以及可选的 GLOSSARY）是唯一事实源；index.html 是机器产物（可选导出），禁止手工修改。
8. 改动 Markdown 后必须立即重新渲染（渲染即审计）；index.html 已存在时会一并更新，不存在不主动生成——用户要分享/归档时才用 `--html` 导出。
9. 渲染器报 BLOCKER 必须当场解决（退出码归零），不带病交付。
10. token 花在翻译上：采集、渲染、审计全部交给脚本，LLM 只做"事实 → 人话"的翻译。
11. **功能划分纪律**：「功能」= 用户能感知、能验证的价值单元（"能记一笔账"）；"写接口""调样式"这类开发步骤不进功能清单，只进 NOW.md 时间线。一个功能确有几块用户可感的组成时，用 FEATURES.md 的 `### 子项:` 表达，不要把步骤摊平成一堆小功能。
12. **用词纪律**：项目解析到术语表时（真实文件名见 `dev-dashboard/.cyd.json` 的 `glossary_file`，不一定叫 GLOSSARY.md），写任何文案先对照它选标准用词；发现自己在用表外新词指代已有事物，先更新术语表或改用标准词，再写正文。
13. **收件箱纪律**：update 模式开头先收 `dev-dashboard/.inbox.jsonl`（面板拍板/指令的兜底），逐条落实后清空；收件箱里的拍板与口头拍板同等效力。
